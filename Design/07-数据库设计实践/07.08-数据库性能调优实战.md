```mermaid
flowchart TD

    M --> B
```

## 2. 性能问题诊断

### 2.1. 慢查询识别

**启用慢查询日志（PostgreSQL）**：

```sql
-- 启用pg_stat_statements扩展
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- 查看慢查询
SELECT
    query,
    calls,
    total_exec_time,
    mean_exec_time,
    max_exec_time,
    (total_exec_time / calls) AS avg_time_per_call
FROM pg_stat_statements
WHERE mean_exec_time > 1000  -- 平均执行时间超过1秒
ORDER BY mean_exec_time DESC
LIMIT 20;
```

**查询执行计划分析**：

```sql
-- 分析查询计划
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT u.username, o.total, o.order_date
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.email = 'user@example.com'
ORDER BY o.order_date DESC
LIMIT 10;

-- 关键指标解读：
-- Seq Scan: 全表扫描，通常需要优化
-- Index Scan: 索引扫描，通常较好
-- Nested Loop: 嵌套循环，小数据集时好
-- Hash Join: 哈希连接，大数据集时好
-- Sort: 排序操作，可能需要索引优化
```

### 2.2. 锁等待分析

**锁等待查询**：

```sql
-- 查看当前锁等待
SELECT
    blocked_locks.pid AS blocked_pid,
    blocked_activity.usename AS blocked_user,
    blocking_locks.pid AS blocking_pid,
    blocking_activity.usename AS blocking_user,
    blocked_activity.query AS blocked_statement,
    blocking_activity.query AS blocking_statement,
    blocked_activity.application_name AS blocked_application,
    blocking_activity.application_name AS blocking_application
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
    AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
    AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

### 2.3. 表统计信息分析

**表大小和统计信息**：

```sql
-- 表大小分析
SELECT
    schemaname,
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS total_size,
    pg_size_pretty(pg_relation_size(schemaname||'.'||tablename)) AS table_size,
    pg_size_pretty(pg_indexes_size(schemaname||'.'||tablename)) AS indexes_size,
    n_live_tup AS row_count,
    n_dead_tup AS dead_rows,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC;

-- 表膨胀检查
SELECT
    schemaname,
    tablename,
    n_dead_tup,
    n_live_tup,
    CASE
        WHEN n_live_tup > 0
        THEN ROUND(100.0 * n_dead_tup / (n_live_tup + n_dead_tup), 2)
        ELSE 0
    END AS dead_tuple_percentage
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY n_dead_tup DESC;
```

## 3. 查询优化实战

### 3.1. JOIN优化

**优化前（慢查询）**：

```sql
-- 问题：没有索引，全表扫描
SELECT u.username, o.total, p.name
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
WHERE u.email = 'user@example.com';
```

**优化后**：

```sql
-- 1. 添加索引
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
CREATE INDEX idx_order_items_product_id ON order_items(product_id);
CREATE INDEX idx_users_email ON users(email);

-- 2. 优化查询（使用EXISTS替代JOIN）
SELECT u.username, o.total, p.name
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
WHERE u.email = 'user@example.com'
  AND EXISTS (
      SELECT 1 FROM order_items oi2
      WHERE oi2.order_id = o.id
  );

-- 3. 或者使用物化视图（如果查询频繁）
CREATE MATERIALIZED VIEW user_order_summary AS
SELECT
    u.id AS user_id,
    u.username,
    u.email,
    o.id AS order_id,
    o.total,
    o.order_date,
    p.name AS product_name
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id;

CREATE INDEX idx_user_order_summary_email ON user_order_summary(email);

-- 定期刷新物化视图
REFRESH MATERIALIZED VIEW CONCURRENTLY user_order_summary;
```

### 3.2. 子查询优化

**优化前**：

```sql
-- 问题：相关子查询，执行N次
SELECT
    u.id,
    u.username,
    (SELECT COUNT(*) FROM orders WHERE user_id = u.id) AS order_count,
    (SELECT SUM(total) FROM orders WHERE user_id = u.id) AS total_spent
FROM users u;
```

**优化后**：

```sql
-- 使用JOIN和聚合
SELECT
    u.id,
    u.username,
    COALESCE(o.order_count, 0) AS order_count,
    COALESCE(o.total_spent, 0) AS total_spent
FROM users u
LEFT JOIN (
    SELECT
        user_id,
        COUNT(*) AS order_count,
        SUM(total) AS total_spent
    FROM orders
    GROUP BY user_id
) o ON u.id = o.user_id;
```

### 3.3. 分页优化

**优化前（深度分页慢）**：

```sql
-- 问题：OFFSET越大越慢
SELECT * FROM orders
ORDER BY order_date DESC
OFFSET 100000 LIMIT 20;
```

**优化后（游标分页）**：

```sql
-- 使用游标分页
SELECT * FROM orders
WHERE order_date < '2024-01-01'  -- 上一页的最后一条记录的order_date
ORDER BY order_date DESC
LIMIT 20;

-- 或者使用索引覆盖
CREATE INDEX idx_orders_date_id ON orders(order_date DESC, id);

SELECT o.*
FROM (
    SELECT id
    FROM orders
    ORDER BY order_date DESC, id DESC
    LIMIT 20 OFFSET 100000
) sub
JOIN orders o ON sub.id = o.id
ORDER BY o.order_date DESC, o.id DESC;
```

## 4. 索引优化实战

### 4.1. 索引使用分析

**索引使用情况查询**：

```sql
-- 未使用的索引
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND schemaname = 'public'
ORDER BY pg_relation_size(indexrelid) DESC;

-- 索引使用统计
SELECT
    schemaname,
    tablename,
    indexname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan DESC;
```

### 4.2. 索引优化案例

**案例1：复合索引优化**:

```sql
-- 查询模式
SELECT * FROM orders
WHERE user_id = 123
  AND status = 'completed'
  AND order_date >= '2024-01-01'
ORDER BY order_date DESC;

-- 优化：创建复合索引
CREATE INDEX idx_orders_user_status_date
ON orders(user_id, status, order_date DESC);

-- 索引列顺序原则：
-- 1. 等值查询列在前（user_id, status）
-- 2. 范围查询列在后（order_date）
-- 3. 排序列在最后（order_date DESC）
```

**案例2：部分索引优化**:

```sql
-- 查询：只查询活跃订单
SELECT * FROM orders WHERE status = 'active';

-- 优化：创建部分索引（只索引活跃订单）
CREATE INDEX idx_orders_active
ON orders(user_id, order_date DESC)
WHERE status = 'active';

-- 优势：索引更小，查询更快
```

**案例3：表达式索引**:

```sql
-- 查询：按邮箱域名查询
SELECT * FROM users WHERE email LIKE '%@gmail.com';

-- 优化：创建表达式索引
CREATE INDEX idx_users_email_domain
ON users((substring(email FROM '@(.+)$')));

-- 或者使用全文搜索
CREATE INDEX idx_users_email_gin
ON users USING GIN (email gin_trgm_ops);
```

## 6. 监控与告警

### 6.1. 性能监控视图

**创建监控视图**：

```sql
-- 慢查询监控视图
CREATE VIEW slow_queries AS
SELECT
    query,
    calls,
    total_exec_time,
    mean_exec_time,
    max_exec_time,
    (total_exec_time / calls) AS avg_time_per_call
FROM pg_stat_statements
WHERE mean_exec_time > 1000
ORDER BY mean_exec_time DESC;

-- 表性能监控视图
CREATE VIEW table_performance AS
SELECT
    schemaname,
    tablename,
    seq_scan,
    seq_tup_read,
    idx_scan,
    idx_tup_fetch,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY seq_scan DESC;
```

### 6.2. 告警规则

**性能告警SQL**：

```sql
-- 慢查询告警
SELECT
    'SLOW_QUERY' AS alert_type,
    query,
    mean_exec_time,
    calls
FROM pg_stat_statements
WHERE mean_exec_time > 5000  -- 5秒
  AND calls > 10;

-- 表膨胀告警
SELECT
    'TABLE_BLOAT' AS alert_type,
    schemaname,
    tablename,
    n_dead_tup,
    ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_percentage
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
  AND ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) > 20;

-- 锁等待告警
SELECT
    'LOCK_WAIT' AS alert_type,
    COUNT(*) AS waiting_queries
FROM pg_locks
WHERE NOT granted;
```

## 8. 实际案例深度分析

### 8.1. 案例1：电商系统性能调优

**背景**：

某电商系统商品搜索查询响应时间>1秒，需要优化到<100ms。

**问题诊断**：

```sql
-- 发现慢查询
SELECT query, mean_exec_time, calls
FROM pg_stat_statements
WHERE query LIKE '%products%'
ORDER BY mean_exec_time DESC
LIMIT 10;

-- 分析执行计划
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM products
WHERE name LIKE '%手机%'
ORDER BY created_at DESC
LIMIT 20;
```

**优化方案**：

1. **创建全文搜索索引**

   ```sql
   CREATE INDEX idx_products_name_gin ON products
       USING gin(to_tsvector('english', name));
   ```

2. **优化查询**

   ```sql
   SELECT * FROM products
   WHERE to_tsvector('english', name) @@ to_tsquery('english', '手机')
   ORDER BY created_at DESC
   LIMIT 20;
   ```

**效果**：

- 查询时间：从1000ms降低到50ms（20x提升）
- 索引命中率：从60%提升到95%

### 8.2. 案例2：金融系统性能调优

**背景**：

某金融系统交易查询在高并发时响应时间>500ms。

**问题诊断**：

```sql
-- 发现锁等待
SELECT
    blocked_locks.pid AS blocked_pid,
    blocking_locks.pid AS blocking_pid,
    blocked_activity.query AS blocked_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity
    ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity
    ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
```

**优化方案**：

1. **使用乐观锁**

   ```sql
   ALTER TABLE accounts ADD COLUMN version INTEGER DEFAULT 0;

   UPDATE accounts
   SET balance = balance + $1,
       version = version + 1
   WHERE id = $2
   AND version = $3;
   ```

2. **批量处理**

   ```sql
   UPDATE accounts
   SET balance = balance + amount
   FROM (VALUES ($1, $2), ($3, $4), ...) AS updates(id, amount)
   WHERE accounts.id = updates.id;
   ```

**效果**：

- 交易延迟：从500ms降低到50ms（10x提升）
- 并发处理能力：提升5x
- 锁等待时间：降低90%

### 8.3. 案例3：社交网络性能调优

**背景**：

某社交网络用户时间线查询响应时间>1秒。

**问题诊断**：

```sql
-- 发现N+1查询问题
SELECT p.* FROM posts p
WHERE p.user_id IN (
    SELECT followee_id FROM relationships WHERE follower_id = $1
)
ORDER BY p.created_at DESC
LIMIT 20;
```

**优化方案**：

1. **使用物化视图**

   ```sql
   CREATE MATERIALIZED VIEW user_timeline AS
   SELECT
       r.follower_id,
       p.id,
       p.content,
       p.created_at
   FROM relationships r
   JOIN posts p ON r.followee_id = p.user_id;

   CREATE INDEX idx_user_timeline_follower_created
       ON user_timeline(follower_id, created_at DESC);
   ```

2. **定期刷新**

   ```sql
   REFRESH MATERIALIZED VIEW CONCURRENTLY user_timeline;
   ```

**效果**：

- 查询时间：从1000ms降低到50ms（20x提升）
- 数据库负载：降低60%

### 10.2. 最新权威资源（2024-2025）

**数据库性能调优研究**：

- **UREM：多维和高维索引的统一增强方法**：2025年10月，研究人员提出了UREM（Unified and Resilient Enhancement Method），这是一种针对多维和高维索引的高性能统一增强方法。UREM能够适应不同场景，提升查询性能，并在静态和动态工作负载下均表现出色。实验结果显示，UREM在静态工作负载下将查询性能提升了最高5.73倍，在动态工作负载下平均提升了5.72倍（arXiv:2510.20110，2025）
- **Delta：基于学习的混合成本查询优化框架**：2025年6月，研究人员发布了Delta框架，旨在解决现有查询优化器在搜索空间爆炸和训练成本高等问题。Delta通过引入兼容查询检测器和两阶段规划器，能够有效地生成高质量的查询计划。实验结果表明，Delta在三个工作负载上实现了比PostgreSQL平均快2.34倍的查询速度，并比现有的学习方法快2.21倍（arXiv:2506.15848，2025）
- **AQETuner：面向分析型查询引擎的可靠查询级配置调优**：2025年4月，研究人员提出了AQETuner，这是一种基于贝叶斯优化的系统，专为分析型查询引擎的查询级配置调优设计。AQETuner通过注意力机制和双任务神经过程模型，能够预测查询性能和失败情况，从而指导调优过程。实验结果显示，AQETuner将查询延迟降低了最多23.7%，查询失败率降低了最多51.2%（arXiv:2504.11756，2025）
- **数据依赖性驱动的查询优化**：2024年6月，研究人员探讨了利用数据依赖性进行查询优化的方法。通过在优化器中集成数据依赖性，能够显著提升数据库系统的吞吐量。实验结果显示，使用所有相关的依赖性，四个标准基准测试的运行时间相比仅使用主外键的情况提高了最多10%，相比不使用依赖性的情况提高了最多22%（arXiv:2406.06886，2024）
